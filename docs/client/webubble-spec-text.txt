This package combines the Programming Languages & Visual Implementation Guide, Street Vendor & Local Commerce Developer 
Addendum, Phase 1 Screen-by-Screen Specification and the 58-task developer register. The separate Unified Master Development 
Specification is intentionally NOT included. 
How the developer must use this document 
1. Read the custom-code rules, technical architecture and visual workflows. 
2. Review all screen-by-screen requirements and the seven original local-commerce categories. 
3. Estimate every numbered task, identify its owner and map its approved screen specification, API endpoint and GitHub pull request. 
4. Build in dependencies order; demonstrate working Android, iOS and website functionality against acceptance criteria. 
5. Submit code, tests, staging evidence, security results and documentation before requesting owner sign-off. 
Mandatory technical baseline 
Mobile apps Dart + Flutter; separate Android/iOS builds from shared mobile code. 
Website and admin TypeScript + React/Next.js; full transactional site, not a catalogue mock-up. 
Backend/API PHP + Laravel, custom modular marketplace logic and documented APIs. 
Database PostgreSQL + SQL migrations; Redis for caching/queues where justified. 
Real-time WebSockets for messaging; WebRTC-based infrastructure for calls/meetings. 
Voice Commerce / AI Dart and TypeScript interfaces; Laravel orchestration; speech/AI services; Python only if 
technically necessary. 
Ownership and quality Webubble-controlled GitHub; no purchased marketplace clones, rebranded e-commerce 
templates, no-code substitutes or static-only prototypes.

Purpose: extend the existing 58-task master register with proposed programming languages, actual implementation work and proof-of-
completion. This is a companion to—not a replacement for—the unified specification. Release classifications remain as recorded in the 
original task register; the product owner must approve pilots and priorities. 
1. Non-negotiable engineering standards 
 Custom-written Webubble business logic and interfaces. No purchased marketplace clones, generic e-commerce themes, no-code 
substitutes or prebuilt dashboard templates. 
 Professional frameworks, libraries and SDKs are allowed with documented licensing, security review and maintainable integration. 
 Source code and deployment pipelines must reside in Webubble-controlled GitHub repositories, with branch protection and pull-
request reviews. 
 One shared backend and consistent data model serve the Android app, iOS app and full transactional website. 
 Registered-business onboarding collects CAC details; informal/local sellers can join without CAC subject to proportionate checks. 
 Voice Commerce means spoken search, voice-assisted listing and language processing; it is not merely a voice call. Internet 
voice/video calls remain a separate communication task.

VC-06 — Voice Commerce 
Proposed release classification: Pilot / controlled rollout; voice notes at launch where supported 
User screens and workflows 
 Buyer: use microphone to search products, dictate a shopping request or describe a Buy for Me order. 
 Seller: dictate a product name, description, price or quick-menu entry, then review before publishing. 
 System: transcribe supported languages, show editable text and require confirmation before creating orders or publishing listings. 
Business and safety rules 
 Voice Commerce is speech-driven shopping/listing, NOT the same as person-to-person voice calling.

 Supported languages and dialects must be explicitly tested; no unsupported accuracy claims.

AF-07 — Advanced Features 
Proposed release classification: Mixed: specified subfeatures below 
User screens and workflows 
 Neighbourhood Basket: group eligible nearby seller items and show separate seller fulfilment. 
 Offline Alerts: queue selected alerts and sync when connectivity resumes; do not promise full offline checkout. 
 Moving Vendors: optional location updates, active route/availability controls and location privacy. 
 Repairs: repair service profiles, quotes, booking/request flow and dispute rules. 
 Custom Orders: customer specifications, seller quote, proof/approval, lead time and revisions. 
Business and safety rules 
 Each subfeature has its own feature flag, risk review and acceptance gate. 
 Moving vendor location sharing requires explicit opt-in, expiry and seller control. 
 Custom-order charges and cancellation terms must be accepted before payment. 
Minimum acceptance tests 
 Neighbourhood basket correctly handles multiple sellers. 
 Moving vendor can disable location sharing instantly. 
 Custom-order quote changes require renewed buyer approval.
